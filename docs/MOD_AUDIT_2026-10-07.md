## Implemented: registry snapshot allocation

The sampled suit provider repeatedly calls PalladiumCore's `ArchRegistryWrapper.getValues()`. The inspected implementation creates a default-capacity `ArrayList` and appends every registrar value, growing/copying its array repeatedly. Beneath the suit provider, `ArrayList.grow` alone accounts for 1.780 exclusive sampled seconds. This is one small part of the 94.772-second provider subtree, not a claim that all of that subtree can be removed.

`ArchRegistryValuesMixin` uses the last completed result's size, capped at 65,536 entries, as the next list's initial capacity. It retains only a numeric hint. Every call still invokes the original registrar traversal, in the original order, into a fresh mutable `ArrayList`. It does not cache suits, equipment, powers, registry members or gameplay results. Growth, shrinkage and same-size replacement are observed on the next call. Iteration failures still propagate; no new registrar queries are introduced. The first/empty call uses the original default allocation behavior.

The optimization applies only when the audited `getValues` body and registrar field match. PalladiumCore targets now pass through the existing compatibility gate instead of the plugin's generic passthrough. Changed/missing code keeps the original path; a version label alone does not authorize or reject it. `heroclock.disablePalladiumOptimizations` also disables this patch. The generator reads the audited nested PalladiumCore JAR directly from the supplied Palladium binary; it does not learn installed code automatically.

Audited PalladiumCore 1.0.1 nested JAR SHA-256: `bea48b57c98e5b40d4163a440b943373c2affcc88bc864e62d6ac5fcf3c412c3`.

This reduces repeated array-growth allocations after warmup. It does not eliminate the registry snapshot allocation, supplier calls, equipment comparisons or registry lookup cost. Target-pack TPS/FPS improvements remain unmeasured.

## OmniOptimizer 1.8.2 coexistence

Audited JAR SHA-256: `b60b0b29d5e9995e8d7c1dd37140d179694b2a1435f522c4b191631f14b6e768`. Its four Java classes provide initialization, optional resource packs and companion APIs; there is no overlapping bytecode optimization for this registry target. Its `registerCompanion(String, String, String[])` API remains compatible with HeroClock's current handshake and merges capabilities. Its runtime script skips its periodic ice fallback when HeroClock is present.

Resource compatibility needs more care than the handshake. Nine active `data/` paths overlap HeroClock; one is byte-identical. Seven differing AlienEvo power files are `galvanic_rod`, `methanosian`, `necrofriggian`, `nucleonix`, `sonorosian`, `tetramand` and `vaxasaurian`. The remaining differing path is the mergeable `minecraft:load` function tag. In all seven files, HeroClock selects `alienevo:omnitrix_timer` while OmniOptimizer selects `omnioptimizer:omnitrix_timer`. Other differences include guarded/local cleanup commands and Echo Echo gameplay definitions. Before 2.2.25, the last selected power definition could restore the AlienEvo timer instead of the OmniOptimizer timer. HeroClock now filters only these seven entries from its own existing mod pack when the matching OmniOptimizer resource passes its individual SHA-256 contract. The hashes match the supplied JAR bytes. This yields the complete audited companion definition, avoiding a partial merge of the different gameplay commands. Without OmniOptimizer, all seven standalone definitions remain available. A missing, unreadable, oversized or changed companion file retains normal resource selection for that path while unchanged files still yield. Version labels do not decide eligibility.

The fix preserves the original mod-pack position and identity, namespaces, metadata, client assets and unrelated resources. It does not install a new top-priority pack or change user datapack ordering. Both mods still contribute their mergeable load tags. Hashing runs at pack creation, with no per-tick or per-selector check. A changed Forge factory signature can omit the optional hook; unchanged factory results are left untouched. This resolves HeroClock's known seven-file interference, not arbitrary conflicts between other packs.

The standalone Necrofriggian loop also drops three redundant existence selectors immediately preceding equivalent `execute as` selectors. The remaining selector naturally handles no matches. Function targets, distance bounds, score thresholds, executor changes and cadence remain intact. The guarded scoreboard command is retained because removing its guard could expose a previously suppressed no-target command error. No Ninjago/FSang commands or OmniOptimizer resources are rewritten.
